A Definitive MVP Roadmap for the Polymarket Whale Alert System: An Architectural Blueprint and Implementation Guide




Introduction




Purpose and Scope


This document consolidates all prior research into a final, actionable Minimum Viable Product (MVP) roadmap. It serves as the canonical guide for developing the Polymarket Whale Alert System, from pre-development infrastructure setup to deployment. The blueprint is optimized for both human strategic understanding and AI-assisted implementation, providing not only prescriptive steps but also the deep, evidence-based rationale behind each critical decision.


The "V2 is V1" Imperative


The central conclusion of the comprehensive research phase is that architectural components initially planned for a future "Version 2.0" are, in fact, immediate, foundational necessities for the MVP.1 The evidence compels a strategic re-prioritization to build a technically viable, scalable, and economically sustainable product from day one. Proceeding with a simpler, architecturally flawed initial build would guarantee a costly and disruptive refactoring effort the moment the system achieved its intended analytical purpose. This roadmap therefore redefines the MVP not as a temporary prototype, but as a production-ready foundation engineered for success.1

Section I: The Finalized Architectural Mandates


This section codifies the non-negotiable, foundational decisions that must be implemented before development begins. It synthesizes the extensive body of research to present the definitive architectural blueprint for the system.


1.1 The Unequivocal Case for Supabase: A Pre-MVP Data Backend Pivot


The selection of a data backend is one of the most consequential decisions in a system's lifecycle, with profound and lasting impacts on performance, cost, and the capacity for future evolution.1 While initial plans considered Google Cloud Platform (GCP) Firestore for its serverless convenience 1, a deeper analysis revealed a fundamental mismatch for the system's core analytical workloads. The evidence overwhelmingly supports a pre-development pivot to a Supabase (PostgreSQL) backend.1


Architectural Mismatch: Relational vs. NoSQL


The system's core value proposition—features like historical Profit & Loss (P&L) tracking, multi-whale confirmation signals, and wallet performance analytics—is inherently relational.1 Data entities such as Whale_Wallets, Trades, and Tracked_Markets are deeply interconnected. Calculating the historical P&L of a single whale, for example, requires joining that wallet's entire trade history with the corresponding resolution data from each market it participated in.1
* Firestore's Failure: As a NoSQL document database, Firestore does not natively support the complex JOIN operations required for these analytics. This forces developers into inefficient workarounds like client-side joins (issuing multiple, separate read requests and combining results in application logic) or data denormalization (storing redundant data copies). These approaches dramatically increase code complexity and, critically, the number of billable read operations, which is a direct symptom of a fundamental architectural mismatch.1
* Supabase's (PostgreSQL) Superiority: Supabase's PostgreSQL foundation is intrinsically aligned with the system's data model. A single, powerful SQL query can perform complex calculations on the database server, leveraging decades of database optimization and returning only the final, aggregated result to the application.1 This approach is vastly more efficient, maintainable, and scalable for the analytical workloads central to the system's purpose. While Supabase offers its own suite of observability and monitoring tools 2, its primary advantage here is the raw power of PostgreSQL, which can be further optimized for read-heavy workloads using advanced techniques like materialized views if future needs dictate.3


Financial Imperative: Deconstructing "Free Tier Fragility"


The architectural mismatch of Firestore translates directly into a predictable and significant financial liability as the system scales.1 A realistic analytical workload, such as performing a daily P&L analysis for 100 tracked whales, would generate at least 50,000 document reads on Firestore. This single daily operation would consume the entire daily free quota of 50,000 reads, leading to a substantial and unpredictable monthly bill that scales directly with the system's usage.1
The same workload on Supabase's Pro plan ($25/month) is fully covered by a flat fee, providing immense cost predictability—a critical strategic asset for a solo developer managing a budget.1 The initial plan to build on Firestore and migrate later is therefore revealed to be a flawed strategy that guarantees hitting a performance and cost wall, forcing an emergency refactoring effort at a critical juncture.1


Strategic Advantage: Mitigating Vendor Lock-In


Beyond the technical and financial benefits, choosing Supabase provides a crucial long-term strategic advantage. Supabase is built on open-source PostgreSQL, providing an ultimate "escape hatch" that allows the entire stack to be self-hosted on any cloud provider or on-premises infrastructure if future requirements change. Firestore, as a proprietary Google service, creates significant vendor lock-in risk.1
Based on this comprehensive analysis, the recommendation is unequivocal: the conceptual data backend must be migrated to Supabase before the first line of MVP code is written. This is a non-negotiable, pre-development architectural decision.1

1.2 Defining the Fortified MVP: A Production-Ready Baseline


The initial MVP concept was a proof-of-concept.1 Subsequent technical due diligence 1 and final analysis 1 mandate a "fortified" architecture engineered for reliability, security, and scalability from its inception.


Resilient Data Ingestion Engine


A critical finding from the due diligence phase revealed that the Polymarket /trades endpoint has a maximum limit parameter of 500, a significant reduction from the 10,000 initially assumed.1 This invalidates any strategy based on large, infrequent batch fetches and necessitates a more resilient polling logic. The finalized architecture must implement a two-mode operation 1:
1. Backfill Mode: A slow, deliberate mode for new markets that paginates through history using limit=500, carefully respecting API rate limits.
2. Steady-State Mode: A frequent, low-impact mode for ongoing monitoring that queries only for trades since the last successful run.
All API calls must be wrapped in robust error handling, specifically implementing an exponential backoff with jitter algorithm to gracefully manage the HTTP 429 Too Many Requests status code and temporary API unavailability.1


Signal Intelligence Core: The Confidence Score Model


The initial proposal for a binary Tier 1/Tier 2 alert system imposes a rigid classification on an inherently probabilistic environment.1 A more powerful and flexible approach is to replace this with a dynamic "Confidence Score" model.1 In this model, each triggered heuristic contributes a weighted value to a cumulative score for a given event. This transforms the output from a simple "alert/no alert" decision into a rich, continuous spectrum of confidence, empowering the operator to set their own notification thresholds. The initial set of weighted heuristics includes Trade Value, Wallet Age, Liquidity Taker vs. Maker, and Preparatory On-Chain Action (e.g., a large SPLIT transaction).1


Hardened Security, Logging, and Operations


The evolution of the project's design reflects a maturation from a hobbyist-level focus on convenience to a professional, defensible security posture. The initial proposal to use Google Sheets as a primary log 1 is definitively rejected. This approach is a severe security anti-pattern, requiring broad permissions and embedded credentials, and is not designed to handle the logging volume of a production system, leading to rate-limiting and silent data loss.1
The correct, production-grade architecture is as follows:
* Logging: GCP Cloud Logging will be the sole, primary log sink. It is secure, automatically captures all function output, is free at the MVP's scale, and provides powerful querying, monitoring, and alerting capabilities far superior to a spreadsheet.1
* Dashboarding: For the user-facing dashboard, structured alert data will be written to a dedicated table in the Supabase database. This data can then be visualized using a free tool like Google Looker Studio, which connects natively to PostgreSQL.1
* Secure CI/CD and Secret Management: Deployments must be automated using GitHub Actions with OpenID Connect (OIDC) for authentication to GCP. This industry best practice eliminates the need for long-lived, static service account keys stored as repository secrets.1 All non-GCP credentials, most notably the Supabase database connection string, must be stored securely in GCP Secret Manager, with the Cloud Function's service account granted the "Secret Manager Secret Accessor" role to retrieve them at runtime.1


1.3 Strategic Hold on Real-Time Ingestion


A migration to a WebSocket-based architecture using Polymarket's Real-Time Data Socket (RTDS) was a key goal for a future version of the system.1 However, this plan must be placed on indefinite hold. This decision is mandated by a meticulous review of the official Polymarket documentation, which explicitly warns that it only offers full support for the "Crypto Prices" and "Comments" topics. Attempting to subscribe to the "activity" or "trades" streams required by the system's core function is not fully supported and may result in unexpected or unreliable behavior.1
Building a core system feature on an officially unsupported API endpoint would introduce an unacceptable level of operational risk, including silent data loss and unpredictable failures.1 This strategic pause demonstrates mature engineering discipline, prioritizing reliability on a supported API over the perceived performance benefits of an unsupported one. This de-risks the project by preventing the allocation of development resources to a fragile system. While the migration is currently blocked, a forward-looking cost analysis for a persistent WebSocket client hosted on Google Cloud Run has been performed, estimating a cost of approximately $9.72 per month, which provides a realistic budget placeholder for future planning when Polymarket officially announces full support for the necessary data streams.1

Section II: The Strategic Roadmap for Post-MVP Evolution


With a robust MVP architecture defined, this section outlines the long-term vision, ensuring that initial development is conducted with a clear understanding of the future path. This phased approach demonstrates a mature strategy for managing technical risk and research and development investment, optimizing for the most constrained resource at each stage of the project.


2.1 Phase 1: Rapid Machine Learning Validation with Vertex AI AutoML


The immediate goal for incorporating machine learning is not to build a perfect model, but to rapidly validate whether an ML-based approach can provide a tangible improvement over the heuristic-based Confidence Score system.1 For a solo developer, time is the most constrained resource during this experimental phase. Therefore, the strategy must optimize for minimizing the time and effort required to obtain a clear go/no-go signal on the viability of ML.1
While Google's Vertex AI AutoML has a higher hourly compute cost than raw infrastructure alternatives, a holistic Total Cost of Ownership (TCO) analysis, which crucially factors in the value of developer time, reveals it to be the significantly cheaper option for initial validation. The high abstraction and automation of AutoML drastically reduce development hours from an estimated 40 hours for a manual implementation to approximately 4 hours for configuration and data preparation.1 This massive reduction in developer overhead makes Vertex AI the fastest and most capital-efficient path to a well-performing baseline model, allowing for a quick decision on the ML initiative.


2.2 Phase 2: Achieving Cost Efficiency and Control with Custom ML on Lambda Labs


Once the ML approach is validated and begins contributing to the system's profitability, the project's priorities will naturally shift. The focus will move from speed-of-validation to long-term cost optimization, model sophistication, and interpretability.1 At this mature stage, the higher recurring compute costs and "black box" nature of AutoML become strategic liabilities.
This is the point at which migrating the now-proven modeling pipeline to a custom-coded solution on a cheaper Infrastructure-as-a-Service (IaaS) platform like Lambda Labs becomes the logical and financially prudent next step.1 The initial, one-time development cost has been justified by the validation phase, and the focus now turns to minimizing the recurring costs of retraining the model. The significantly lower hourly GPU rates offered by IaaS providers will dramatically reduce long-term operational expenses.1 Furthermore, a custom implementation provides granular control over the model architecture, enables deeper interpretability, and allows for the implementation of more advanced MLOps practices as the system scales.1 This two-phase approach represents a strategic arbitrage of ML platforms, leveraging each for its unique strengths at the appropriate stage of the project's lifecycle to optimize for the most critical resource at that time: developer velocity in Phase 1, and operational cost in Phase 2.

Section III: The Prescriptive Pre-Development and MVP Action Plan


This section provides a direct, prescriptive, and sequential checklist of tasks to be completed. It translates all preceding analysis into a prioritized action plan designed to be directly consumable by both the developer and AI coding agents to de-risk the project and establish a solid foundation for success. The plan deliberately front-loads foundational infrastructure and security work, ensuring that all subsequent code is built upon a solid, production-ready base.


Phase 1: Foundational Setup & Architecture (1-2 Days)


1. Provision Supabase Project: Create a new project on the Supabase Pro plan to gain access to necessary production features and avoid the inactivity pause. Securely record the database connection string.1
2. Define Relational Schema: Design and implement the initial PostgreSQL schema within Supabase. Create tables for Whale_Wallets, Trades, and Tracked_Markets, establishing the necessary foreign key relationships to model the system's data correctly.1
3. Provision GCP Project: Create a new Google Cloud Platform project. In the API Library, enable all necessary services: Cloud Functions, Cloud Scheduler, Secret Manager, and Cloud Logging.1
4. Configure Secure Deployment: Establish a trust relationship between the GCP project and a new private GitHub repository by configuring Workload Identity Federation with OIDC. Create a dedicated deployment service account and grant it the most restrictive set of IAM roles necessary for its function (e.g., "Cloud Functions Developer," "Service Account User," "Secret Manager Secret Accessor"). Store the Supabase connection string in GCP Secret Manager and grant the service account access to it.1


Phase 2: Core Logic & Algorithm Finalization (3-5 Days)


1. Develop Data Ingestion Module: Implement the two-mode (backfill/steady-state) polling logic in Python. Ensure the implementation correctly handles the verified Polymarket API limits and includes robust error handling with exponential backoff for rate-limiting responses.1
2. Implement Confidence Score Algorithm: Code the core detection logic based on the weighted "Confidence Score" model. All heuristic weights (e.g., for trade value, wallet age, liquidity-taking) and thresholds should be stored in a configuration file to allow for easy tuning.1
3. Develop Data Persistence Logic: Write the data access layer of the application to interact with the Supabase PostgreSQL database. Use a standard, well-supported Python library such as psycopg2 or an ORM like SQLAlchemy.1
4. Set up Logging and Alerting: Configure the Cloud Function to write all structured logs exclusively to GCP Cloud Logging. Implement the chosen alerting mechanism, such as sending a formatted JSON payload to a Discord or Slack webhook.1


Phase 3: Backtesting & Pre-Launch Validation (5-10 Days)


This phase reflects a mature understanding that a financial tool's viability must be proven quantitatively on a large dataset before it can be trusted. A significant portion of the timeline is dedicated to this rigorous, data-driven validation.
1. Implement Historical Backtesting Framework: As a critical pre-launch validation step, build a script that utilizes the data ingestion module to pull the complete trade history of several already-resolved Polymarket markets.1
2. Run and Tune Algorithm: Execute the Confidence Score algorithm against this historical dataset. Programmatically analyze the profitability of the signals that would have been generated.1
3. Iterate and Refine: Use the quantitative results from the backtest to tune the heuristic weights and thresholds in the algorithm's configuration. The goal is to optimize the model for signal quality and profitability, establishing a baseline performance metric (e.g., expected return on investment per signal) before any live operation.1


Phase 4: Final Go/No-Go Decision & MVP Deployment


The decision to launch will be based on empirical evidence, not guesswork.
1. Review Backtesting Results: Compare the algorithm's final, tuned baseline performance against pre-defined success criteria. This data-driven review will determine if the strategy is viable.1
2. Final Decision: Make a formal go/no-go decision to proceed with live deployment based on the empirical evidence from the backtest.1
3. Deploy MVP: If the decision is "go," use the pre-configured secure CI/CD pipeline in GitHub Actions to deploy the Cloud Function. Activate the Cloud Scheduler job to begin the live "System Validation" phase, where the system operates in a live environment, logging its actions and generated alerts for final monitoring before any capital is committed.1
